# 5. 회고

Loop를 직접 설계하고 구현하며, 코드와 Diff 요약, Report 등의 Evidence를 리뷰하는 방식으로 팀 프로젝트를 진행했습니다.

이번 팀 프로젝트를 진행하면서 느꼈던 점을 팀원별로 적어 주세요.

| 팀원 이름 | 좋았던 점 | 아쉬웠던 점 |
|---|---|---|
| 전예리 프로 (팀장) | Loop(prepare → implement → verify)로 기능 개발을 진행하면서, 단계별 증거가 작업마다 남아 나중에 근거를 되짚을 수 있었습니다.<br>리뷰를 통해서 혼자였으면 놓쳤을 것들이 잡혔습니다. 제가 놓친 위험과 충돌도 merge 전에 고칠 수 있었습니다.<br>모든 팀원들이 적극적으로 참여해 주셔서 좋았습니다.<br>이번 프로젝트를 통해 배운 점을 실제 업무에도 반영하면 더 좋은 코드를 만들 수 있는 계기가 될 것 같습니다. | PR이 너무 커서(파일 30개) 리뷰어가 나눠 보기 어려웠습니다.<br>첫 E2E 실행에서만 나는 불안정을 완전히 해결했다고 말하기에는 부족한 것 같습니다.<br>에이전트 정의를 고치고 `/reload-skills`를 하지 않아 옛 정의로 돈 적이 있었습니다. |
| 장영은 프로 | (본인 작성) | (본인 작성) |
| 정혜미 프로 | (본인 작성) | (본인 작성) |
| 허주 프로 | Loop를 Workflow로 돌려 보니, 점검 단계가 제가 놓친 문서 규칙 충돌("확정 후 주문 수정 제외")을 스스로 찾아냈습니다. 구현 전에 요구를 먼저 정해 두어서 구현도 한 번에 통과했습니다.<br>리뷰 덕분에 혼자였으면 놓쳤을 것을 잡았습니다. 팀원이 전체 E2E에서 가끔 실패하는 시험을 찾아 주셔서, 원인을 재현해 고칠 수 있었습니다.<br>PR이 여러 개 동시에 올라올 때, 머지 전에 실제로 합쳐 보고 충돌과 머지 순서를 팀과 미리 의논해서 큰 문제 없이 합칠 수 있었습니다. | 처음에는 Loop를 Workflow로 돌리지 않고 단계만 흉내 내어 직접 진행했다가, 처음부터 다시 했습니다.<br>점검 결과에 "기존 규칙과 충돌 없음"이라고 잘못 쓴 적이 있어서, 문서를 끝까지 확인하는 습관이 필요하다고 느꼈습니다.<br>여러 PR이 같은 문서(PRD·INTENT)를 고쳐서, 합칠 때마다 충돌을 정리해야 했습니다.<br>Loop 로그 원본이 임시 폴더에만 있어서, 옮겨 적은 로그를 증거로 올려야 했습니다. |
