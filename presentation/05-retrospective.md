# 5. 회고

Loop를 직접 설계하고 구현하며, 코드와 Diff 요약, Report 등의 Evidence를 리뷰하는 방식으로 팀 프로젝트를 진행했습니다.

이번 팀 프로젝트를 진행하면서 느꼈던 점을 팀원별로 적어 주세요.

| 팀원 이름 | 좋았던 점 | 아쉬웠던 점 |
|---|---|---|
| 전예리 프로 (팀장) | Loop(prepare → implement → verify)로 기능 개발을 진행하면서, 단계별 증거가 작업마다 남아 나중에 근거를 되짚을 수 있었습니다.<br>리뷰를 통해서 혼자였으면 놓쳤을 것들이 잡혔습니다. 제가 놓친 위험과 충돌도 merge 전에 고칠 수 있었습니다.<br>모든 팀원들이 적극적으로 참여해 주셔서 좋았습니다.<br>이번 프로젝트를 통해 배운 점을 실제 업무에도 반영하면 더 좋은 코드를 만들 수 있는 계기가 될 것 같습니다. | PR이 너무 커서(파일 30개) 리뷰어가 나눠 보기 어려웠습니다.<br>첫 E2E 실행에서만 나는 불안정을 완전히 해결했다고 말하기에는 부족한 것 같습니다.<br>에이전트 정의를 고치고 `/reload-skills`를 하지 않아 옛 정의로 돈 적이 있었습니다. |
| 장영은 프로 | 인증·권한처럼 위험한(Red) 변경을 Loop(prepare → implement → verify)로 진행하니, 위험 표와 체크리스트·report가 남아 리뷰어가 근거를 따라가며 확인할 수 있었습니다.<br>Gate 리뷰에서 가입·로그인 횟수 제한, 세션 ID 재발급 같은 빠진 부분이 머지 전에 잡혔고, 고친 것은 테스트로(`changeSessionId()`를 끄면 E2E-044 실패) 확인했습니다.<br>Loop와 워크플로우를 계속 수정해 가면서 개선해 나갈 수 있어서 좋았습니다.<br>고객사 PR(#29)을 세 차례 리뷰하며 작성자 판정 규칙이 두 곳에 있는 문제를 짚었고, 작성자가 반영한 뒤 Gate로서 반영 여부까지 다시 확인하는 흐름이 좋았습니다. | 처음 구현에는 횟수 제한·세션 재발급이 없었고, 높음 위험이 GO여도 경고 칸이 비어 있었습니다. 인증 영역은 처음부터 이런 항목을 체크리스트에 넣었어야 했습니다.<br>리뷰를 더 꼼꼼하게 보고 싶었지만 일정상 PR마다 충분한 시간을 내기 어려웠습니다. |
