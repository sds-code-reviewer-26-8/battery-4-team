# 1. 테스트 세팅

**신규 추가 기능 4개(고객사 이름, 필요 납기일, 회원 가입, 공장 운영비)를 중심으로, 기존 기능(경로 계산, 주문)까지 여러 겹의 시험으로 확인했습니다.**

- 규칙대로 동작하는지, 이상한 입력과 많은 사용자에도 오류 없이 동작하는지 보았습니다.
- 그 과정에서 결함 3건을 찾아 고쳤고, 사용자가 몰릴 때 주문 목록이 가장 느리다는 점도 알아냈습니다.
- 목적은 **새 기능을 더하거나 기존 기능을 수정하더라도 시스템이 정상적으로 잘 동작하는지 확인하는 것**입니다.

| 테스트 | 개수 | 테스트 도구 |
|---|:-:|---|
| Unit Test | 26개 | JUnit 5 |
| Slice Test | 40개 | JUnit 5 + Spring Boot Test (`@WebMvcTest`, `@DataJpaTest`) |
| 통합 테스트 | 56개 | JUnit 5 + Spring Boot Test (`@SpringBootTest`) |
| E2E 테스트 | 87개 | Playwright |
| Robustness(견고성) 테스트 | 6개 | JUnit 5 |
| Stress 테스트 | 3개 시나리오 | Apache JMeter |
| 성능 테스트 | 6개 | JUnit 5 (시간 측정) |
| Test Coverage | 라인 95.3% (분기 93.8%) | JaCoCo |

<br>

## 테스트별 점검 기능과 결과

| 종류 | 대상 | 점검 기능 | 점검 결과 | 왜 필요한가 |
|---|---|---|---|---|
| **Unit** (26개) | 기존 + 신규 | · 경로 계산(공장 운영비 반영 포함)<br>· 마스터 입력값의 억 원 단위 변환<br>· 가입·로그인 요청 횟수 제한<br>· 납기 초과 일수 계산 | 26건 모두 통과 | 계산과 규칙이 맞는지 가장 빠르게 확인하기 위해 |
| **Slice** (40개) | **신규** | **신규 기능 4개**의 요청·응답과 DB 컬럼만 확인<br>· 고객사: 로그인 없이는 수정 불가, 작성자에게만 수정 가능 표시<br>· 필요 납기일: 정수만 받음(5.5나 문자는 거부), 생략하면 "가능한 빨리"<br>· 회원 가입: 로그인 없이 가입, 로그인 때 세션 교체, 가입 횟수 제한<br>· 공장 운영비: 억 원 단위로 표시, 틀린 값은 이유를 모아 알림<br>· DB 컬럼: 새 컬럼에 값이 저장되고 읽힘(비워 둔 값 포함) | 40건 모두 통과<br>운영 코드를 일부러 망가뜨린 7가지를 모두 잡아냄 | 기존 전체가 아니라 신규 기능만 대상으로, 서비스 규칙은 가짜로 빼서 입구(요청·응답)와 출구(DB)의 문제만 따로 확인하기 위해 |
| **통합** (56개) | **신규 중심** | · 주문 확정·상태 변경<br>· 고객사: 작성자만 수정, 100자 제한, 완료 후 수정 불가<br>· 필요 납기일: 정수만, 경계값<br>· 가입·로그인: 암호화해 저장, 세션<br>· 공장 운영비: 값 범위 검사, 확정한 주문은 그대로<br>· 부하 시험용 기능(`stress` 모드에서만 열림) | 56건 모두 통과 | 서비스와 DB가 함께 규칙대로 동작하는지 확인하기 위해 |
| **E2E** (87개) | 기존 + 신규 | · 기존 흐름: 로그인·접근 통제, 주문 수량 입력, 경로안 비교, 주문 확정, 목록·상세, 상태 관리, 마스터 수정<br>· **신규 기능 4개 모두**를 화면에서 처음부터 끝까지 (아래 "신규 기능 E2E" 참고) | 87건 모두 통과<br>(1건은 알려진 결함이라 "실패해야 통과") | 사용자가 실제로 쓰는 흐름이 화면에서 되는지 확인하기 위해 |
| **Robustness(견고성)** (6개) | 기존 흐름 | · 경로 계산(운항비와 공장 운영비): 배 1~4척 × 주문 조합 전체<br>· 비정상 입력과 동시 요청: 이상한 수량, 깨진 요청(가입·로그인·확정), 동시 확정, 잘못된 상태·고객사 변경 | 6건 모두 통과<br>**결함 3건을 찾아 고침** (아래 "테스트로 찾은 결함" 참고) | 어떤 조합과 입력에서도 서버 오류 없이 정해진 응답을 주고 데이터가 어긋나지 않는지 확인하기 위해 |
| **성능** (6개) | 기존 흐름 | · 경로 계산<br>· 시뮬레이션 요청<br>· 동시 요청(사용자 8명)<br>· 주문 1,000건 목록 조회(고객사·납기 열 포함) | 6건 모두 통과<br>한도에 여유가 있음 (아래 측정값 참고) | 코드를 바꿨을 때 응답이 눈에 띄게 느려지는 것을 잡기 위해 |
| **Stress** (3개 시나리오) | 기존 흐름 | · 사용자가 한꺼번에 몰려도 오류 없이 동작하는지<br>· 어떤 기능이 가장 느린지<br>· ① 로그인 없이 경로 계산·상태 확인<br>· ② 로그인 후 주문 목록·상세 조회<br>· ③ 경로 계산 후 주문 확정 | 오류 0건 (아래 결과 참고)<br>가장 느린 곳은 **주문 목록** | 평소보다 훨씬 많은 사용자가 몰리는 상황을 미리 겪어 보기 위해. 시험용 기능은 `stress` 모드로 띄운 앱에서만 열립니다. |

추가한 JUnit 108건의 대상은 다음과 같습니다.

- **90건은 신규 기능용**입니다.
- 18건은 성능·견고성·부하 시험용입니다.
- 늘어난 E2E도 모두 신규 기능을 대상으로 합니다.

성능·견고성·Stress는 기존 흐름(경로 계산, 주문 확정·목록)을 대상으로 하되, 신규 항목(고객사·납기 열, 가입 요청)도 일부 포함합니다.

<br>

## 테스트로 찾은 결함

Robustness(견고성) 시험이 이상한 입력을 일부러 보내서 찾아낸 결함 3건입니다. 모두 고쳤습니다.

| 발견한 결함 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 상태 변경 요청에서 상태가 비어 있음 | 서버 오류(500) | 이유를 알려 주는 400 |
| 수량에 소수(1.5)를 입력 | 그대로 받아들임(200) | 400으로 거부 |
| 숫자·참/거짓 값으로 가입 | 가입됨(200) | 400으로 거부 |

- 고친 곳을 일부러 되돌려 보면 해당 시험이 실패합니다. 같은 결함이 다시 생기면 바로 알 수 있습니다.

## 성능 테스트: 측정값과 한도

이 PC에서 잰 값이며, PC마다 다릅니다. (p95는 느린 쪽 5%를 뺀 가장 느린 값, 즉 95%의 요청이 이 시간 안에 끝난다는 뜻입니다.)

| 점검 | 측정값 | 한도 |
|---|---|---|
| 경로 계산(기본 수량, 배 1~4척) | 중앙값 0.4~1.2ms | 중앙값 200ms |
| 경로 계산(최대 수량 근처) | 중앙값 5~10ms | 중앙값 200ms |
| 시뮬레이션 요청 | p95 약 11ms | p95 300ms |
| 동시 요청(사용자 8명, 104건) | 전체 약 160ms | 5초 |
| 주문 1,000건 목록 조회 | p95 약 44ms | p95 300ms |

- 한 건씩 요청하면 주문 1,000건 목록도 빠릅니다.
- Stress에서는 주문이 계속 늘어나(최대 약 3,700건) 280명이 동시에 요청했고, 목록의 평균은 1.8초였습니다.
- 한 건씩은 빠르지만, 주문이 쌓이고 사용자가 몰리면 느려졌습니다.

<br>

## Stress 테스트 결과

JMeter로 두 번 부하를 줬습니다. 1차는 사용자가 요청 사이에 쉬는 보통 부하, 2차는 280명이 쉬지 않고 요청하는 부하입니다.

같은 PC에서 시험 도구와 서버를 함께 돌렸습니다.

| 항목 | 1차: 보통 | 2차: 많이 몰림 |
|---|---|---|
| 가상 사용자 | 70명 (읽기 50 + 로그인 후 읽기 10 + 주문 확정 10) | 280명 (읽기 200 + 로그인 후 읽기 40 + 주문 확정 40) |
| 실행 시간 | 약 2분 (사용자 증가 30초, 유지 120초로 설정) | 약 2분 (사용자 증가 30초, 유지 120초로 설정) |
| 쉬는 시간 | 요청마다 0.5~1초 | 없음(계속 요청) |
| 보낸 요청 | 4,891건 | 37,859건 |
| 오류 | **0건** | **0건** |
| 평균 응답 시간 | 0.007초 | 0.8초 |
| 처리량 | 평균 초당 약 40건 | 평균 초당 약 300건 |

**시나리오별 결과** (각 시나리오에서 가장 느린 요청의 평균 응답 시간)

| 시나리오 | 가장 느린 요청 | 1차 | 2차 |
|---|---|---|---|
| ① 로그인 없이 경로 계산·상태 확인 | 1차 경로 계산, 2차 상태 확인 | 0.007초 | 1.0초 |
| ② 로그인 후 주문 목록·상세 조회 | 주문 목록 | 0.018초 | 1.8초 |
| ③ 경로 계산 후 주문 확정 | 주문 확정 | 0.008초 | 0.6초 |

- 280명이 쉬지 않고 요청해도 **오류는 한 건도 없었습니다.**
- 1차는 요청 사이에 쉬어서, 70명이 동시에 요청한 것은 아닙니다.
- 가장 느린 것은 **주문 목록**입니다(2차 평균 1.8초). 주문이 쌓일수록 목록이 무거워질 수 있어 앞으로 살펴볼 부분입니다.
- 한 대의 PC에서 돌린 결과라 서버의 정확한 한계는 아닙니다.
- 결과 리포트: 1차 `docs/jmeter/20261023_stress_50threads/index.html`, 2차 `docs/jmeter/20261023_stress_200threads/index.html` (폴더 이름의 50, 200은 읽기 그룹의 사용자 수)

## 신규 기능 E2E

신규 추가 기능 4개를 화면에서 확인한 E2E는 모두 **39건**입니다. (E2E 87건 중)

| 기능 | 시험 수 | 화면에서 확인한 흐름 |
|---|:-:|---|
| 고객사 이름 | 4개 | 입력해 확정하면 상세·목록에 보이고, 상세에서 수정<br>비우면 "-"로 보임, 101자는 거부되고 100자는 허용<br>완료 상태에서는 수정할 수 없음, HTML 문자는 글자 그대로 표시 |
| 필요 납기일 | 24개 | 기본은 "가능한 빨리", 납기를 넘는 안은 빨간색과 "납기 초과" 글자로 표시<br>잘못된 값(4·51·0·-5·10.5·abc)은 오류 문구를 보임<br>확정하면 납기가 저장되어 목록·상세에 보임 |
| 회원 가입 | 3개 | 가입한 뒤 로그인할 수 있고, 로그인 전에는 여전히 막힘<br>한도를 넘으면 이유가 화면에 보임<br>로그인하면 세션 ID가 바뀜 |
| 공장 운영비 | 8개 | 안마다 운영비가 보이고, 총 비용 = 생산 원가 + 운항비 + 운영비<br>확정한 주문은 확정 당시 운영비가 그대로 유지<br>마스터에서 운영비를 바꾸면 새 계산에 반영되고, 범위 밖 값은 저장하지 않음 |
