# 1. 테스트 세팅

**신규 추가 기능 4개를 여러 겹의 시험으로 확인했습니다.** 규칙대로 동작하는지, 이상한 입력과 많은 사용자에도 오류 없이 동작하는지 보았습니다. 그 과정에서 결함 3건을 찾아 고쳤고, 주문이 많아지면 목록이 느려진다는 점도 알아냈습니다. 목적은 **기능을 바꿔도 깨지지 않는다는 확신**을 얻는 것입니다.

| 테스트 | 개수 | 테스트 도구 |
|---|:-:|---|
| Unit Test | 26개 | JUnit 5 |
| Slice Test | 40개 | JUnit 5 + Spring Boot Test (`@WebMvcTest`, `@DataJpaTest`) |
| 통합 테스트 | 56개 | JUnit 5 + Spring Boot Test (`@SpringBootTest`) |
| E2E 테스트 | 87개 | Playwright |
| Robustness 테스트 | 6개 | JUnit 5 |
| Stress 테스트 | 1개 | Apache JMeter |
| 성능 테스트 | 6개 | JUnit 5 (시간 측정) |
| Test Coverage | 라인 95.3% (분기 93.8%) | JaCoCo |

<br>

## 테스트별 점검 기능과 결과

| 종류 | 점검 기능 | 점검 결과 | 왜 필요한가 |
|---|---|---|---|
| **Unit** (26개) | 경로 계산(공장 운영비 반영 포함), 마스터 입력값의 억 원 단위 변환, 가입·로그인 요청 횟수 제한, 납기 초과 일수 계산 | 26건 모두 통과 | 계산과 규칙이 맞는지 가장 빠르게 확인하기 위해 |
| **Slice** (40개) | **새로 만든 기능 4개**의 요청·응답과 DB 컬럼만 확인<br>· 고객사: 로그인 없이는 수정 불가, 작성자에게만 수정 가능 표시<br>· 필요 납기일: 정수만 받음(5.5나 문자는 거부), 생략하면 "가능한 빨리"<br>· 회원 가입: 로그인 없이 가입, 로그인 때 세션 교체, 가입 횟수 제한<br>· 공장 운영비: 억 원 단위로 표시, 틀린 값은 이유를 모아 알림<br>· DB 컬럼: 새 컬럼에 값이 저장되고 읽힘(비워 둔 값 포함) | 40건 모두 통과<br>운영 코드를 일부러 망가뜨린 7가지를 모두 잡아냄 | 기존 전체가 아니라 신규 기능만 대상으로, 서비스 규칙은 가짜로 빼서 입구(요청·응답)와 출구(DB)의 문제만 따로 확인하기 위해 |
| **통합** (56개) | 주문 확정·상태 변경, 고객사(작성자만 수정, 100자 제한, 완료 후 수정 불가), 필요 납기일(정수만, 경계값), 가입·로그인(암호화해 저장, 세션), 공장 운영비(값 범위 검사, 확정한 주문은 그대로), 부하 시험용 기능(`stress` 모드에서만 열림) | 56건 모두 통과 | 서비스와 DB가 함께 규칙대로 동작하는지 확인하기 위해 |
| **E2E** (87개) | 로그인·접근 통제, 주문 수량 입력, 경로안 비교, 주문 확정, 목록·상세, 상태 관리, 마스터 수정, 그리고 **신규 추가 기능 4개 모두**를 화면에서 처음부터 끝까지 | 87건 모두 통과<br>(1건은 알려진 결함이라 "실패해야 통과") | 사용자가 실제로 쓰는 흐름이 화면에서 되는지 확인하기 위해 |
| **Robustness** (6개) | 경로 계산(운항비와 공장 운영비): 배 1~4척 × 주문 조합 전체<br>비정상 입력과 동시 요청: 이상한 수량, 깨진 요청(가입·로그인·확정), 동시 확정, 잘못된 상태·고객사 변경 | 6건 모두 통과<br>**결함 3건을 찾아 고침** | 어떤 조합과 입력에서도 서버 오류 없이 정해진 응답을 주고 데이터가 어긋나지 않는지 확인하기 위해 |
| **성능** (6개) | 경로 계산, 시뮬레이션 요청, 동시 요청(사용자 8명), 주문 1,000건 목록 조회(고객사·납기 열 포함) | 6건 모두 통과<br>한도에 여유가 있음 (주문 1,000건 목록 p95 약 50ms, 한도 300ms. 이 PC 기준) | 코드를 바꿨을 때 응답이 눈에 띄게 느려지는 것을 잡기 위해 |
| **Stress** (1개) | 사용자가 한꺼번에 몰려도 오류 없이 동작하는지, 어떤 기능이 가장 먼저 느려지는지<br>· 경로 계산, 주문 목록·상세 조회, 주문 확정을 동시에 요청 | 오류 0건 (아래 결과 참고)<br>가장 먼저 느려진 곳은 **주문 목록** | 평소보다 훨씬 많은 사용자가 몰리는 상황을 미리 겪어 보기 위해. 시험용 기능은 `stress` 모드로 띄운 앱에서만 열립니다. |

<br>

## Stress 테스트 결과

JMeter로 사용자를 늘려 가며 부하를 줬습니다. 같은 PC에서 시험 도구와 서버를 함께 돌렸습니다.

| | 1차: 보통 | 2차: 많이 몰림 |
|---|---|---|
| 동시 사용자 | 70명 | 280명 |
| 쉬는 시간 | 요청마다 0.5~1초 | 없음(계속 요청) |
| 보낸 요청 | 4,862건 | 37,859건 |
| 오류 | **0건** | **0건** |
| 평균 응답 시간 | 0.007초 | 0.8초 |

- 사용자가 4배 가까이 늘고 쉬지 않고 요청해도 **오류는 한 건도 없었습니다.**
- 2차에서는 처음엔 빠르다가(초당 559건) 요청이 쌓이면서 초당 약 200건으로 느려졌습니다.
- 가장 먼저 느려진 것은 **주문 목록**입니다(평균 1.8초). 주문이 많아질수록 목록이 무거워질 수 있어 앞으로 살펴볼 부분입니다.
- 한 대의 PC에서 돌린 결과라 서버의 정확한 한계는 아닙니다.
- 결과 리포트: `docs/jmeter/20261023_stress_200threads/index.html`

## 테스트 커버리지

JUnit 134건을 실행하며 측정했습니다.

| 구분 | 커버 / 전체 | 비율 |
|---|:-:|:-:|
| 라인 | 954 / 1,001 | 95.3% |
| 분기 | 332 / 354 | 93.8% |

![JaCoCo 커버리지 요약](assets/coverage.png)

- 가장 높은 곳은 경로 계산 코드로, 라인 97.6%·분기 97.0%입니다.
- 낮은 곳은 요청 횟수 제한 일부(81%), 페이지 연결(82%), 앱 시작 코드입니다.
- JUnit 기준이며, E2E는 포함하지 않았습니다.
