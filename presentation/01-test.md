# 1. 테스트 세팅

| 테스트 | 개수 | 테스트 도구 |
|---|:-:|---|
| Unit Test | 26개 | JUnit 5 |
| Slice Test | 40개 | JUnit 5 + Spring Boot Test (`@WebMvcTest`, `@DataJpaTest`) |
| 통합 테스트 | 49개 | JUnit 5 + Spring Boot Test (`@SpringBootTest`) |
| E2E 테스트 | 87개 | Playwright |
| Robustness 테스트 | 6개 | JUnit 5 |
| Stress 테스트 | 0개 | - |
| 성능 테스트 | 6개 | JUnit 5 (시간 측정) |
| Test Coverage | 라인 95.1% (분기 93.9%) | JaCoCo |

- JUnit 127건과 E2E 87건이 모두 통과합니다.
- E2E 중 1건은 알려진 결함(없는 주문 번호로 접속하면 오류 화면이 뜸)이라 "실패해야 통과"로 표시했습니다.

<br>

## 테스트별로 무엇을 확인했나

| 종류 | 어떤 기능을 확인했나 | 왜 필요한가 |
|---|---|---|
| **Unit** (26개) | 경로 계산(공장 운영비 반영 포함), 마스터 입력값의 억 원 단위 변환, 가입·로그인 요청 횟수 제한, 납기 초과 일수 계산 | 계산과 규칙이 맞는지 가장 빠르게 확인하기 위해 |
| **Slice** (40개) | **새로 만든 기능 4개**의 요청·응답과 DB 컬럼만 확인<br>· 고객사: 로그인 없이는 수정 불가, 작성자에게만 수정 가능 표시<br>· 필요 납기일: 정수만 받음(5.5나 문자는 거부), 생략하면 "가능한 빨리"<br>· 회원 가입: 로그인 없이 가입, 로그인 때 세션 교체, 가입 횟수 제한<br>· 공장 운영비: 억 원 단위로 표시, 틀린 값은 이유를 모아 알림<br>· DB 컬럼: 새 컬럼에 값이 저장되고 읽힘(비워 둔 값 포함) | 기존 전체가 아니라 신규 기능만 대상으로, 서비스 규칙은 가짜로 빼서 입구(요청·응답)와 출구(DB)의 문제만 따로 확인하기 위해 |
| **통합** (49개) | 주문 확정·상태 변경, 고객사(작성자만 수정, 100자 제한, 완료 후 수정 불가), 필요 납기일(정수만, 경계값), 가입·로그인(암호화해 저장, 세션), 공장 운영비(값 범위 검사, 확정한 주문은 그대로) | 서비스와 DB가 함께 규칙대로 동작하는지 확인하기 위해 |
| **E2E** (87개) | 로그인·접근 통제, 주문 수량 입력, 경로안 비교, 주문 확정, 목록·상세, 상태 관리, 마스터 수정, 그리고 **기능 4개 모두**를 화면에서 처음부터 끝까지 | 사용자가 실제로 쓰는 흐름이 화면에서 되는지 확인하기 위해 |
| **Robustness** (6개) | 경로 계산(운항비와 공장 운영비): 배 1~4척 × 주문 조합 전체<br>비정상 입력과 동시 요청: 이상한 수량, 깨진 요청(가입·로그인·확정), 동시 확정, 잘못된 상태·고객사 변경 | 어떤 조합과 입력에서도 서버 오류 없이 정해진 응답을 주고 데이터가 어긋나지 않는지 확인하기 위해. 이 시험으로 결함 3건을 찾아 고쳤습니다. |
| **성능** (6개) | 경로 계산, 시뮬레이션 요청, 동시 요청(사용자 8명), 주문 1,000건 목록 조회(고객사·납기 열 포함) | 코드를 바꿨을 때 응답이 눈에 띄게 느려지는 것을 잡기 위해 (한도는 여유 있게 설정) |
| **Stress** (0개) | 하지 않았습니다 | 한계까지 부하를 올리는 시험은 하루 일정에서 기능 구현과 리뷰를 우선하느라 제외했습니다. 대신 성능 테스트에서 보통 수준의 동시 요청은 확인했습니다. |

운영 코드를 일부러 망가뜨려 보았더니(고객사 이름 누락, 납기 실수 허용, 로그인 확인 제거 등 7가지) Slice Test가 모두 실패해서, 테스트가 실제로 문제를 잡아냅니다.

<br>

## 테스트 커버리지

JUnit 127건을 실행하며 측정했습니다.

| 구분 | 커버 / 전체 | 비율 |
|---|:-:|:-:|
| 라인 | 893 / 939 | 95.1% |
| 분기 | 310 / 330 | 93.9% |

![JaCoCo 커버리지 요약](assets/coverage.png)

- 가장 높은 곳은 경로 계산 코드로, 라인 97.6%·분기 97.0%입니다.
- 낮은 곳은 요청 횟수 제한 일부(81%), 페이지 연결(82%), 앱 시작 코드입니다.
- JUnit 기준이며, E2E는 포함하지 않았습니다.

<br>
