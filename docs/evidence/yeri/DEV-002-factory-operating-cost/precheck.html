1판단

GO: 공장 운영비는 문서에 근거가 있는 새 기능이고, 직전 점검의 질문 4개에 사용자가 답해 빈칸이 없다. 승인된 계획대로 구현한다.

이유

  • 개발 근거 있음: PRD 9장 공장 운영비 항목에 6가지 결정이 확정돼 있고 PRD 6장이 9장을 가리킨다. INTENT 8.4에 같은 방향이 있다. PRD 10장 범위 밖과 무관하다.
  • 직전 점검(DEV-002)의 질문 4개에 사용자가 답했다: 동일 안 안내를 넣는다, 하루 운영비 상한은 1,000억 원 이하, 비개발자용 안내서는 이번에 고치지 않는다, 운영 일수의 끝은 그 공장의 마지막 수거일이다.
  • 답으로 정해진 두 가지(동일 안 안내, 1,000억 원 상한)는 요구 변경이 아니라 PRD 9장의 빈칸을 채운 것이라 PRD 9장에 반영한다.
  • 경고(진행): 변경이 크다(여러 계층, DB 컬럼 추가, 마스터 버전·확정 스냅샷·총 비용 정의 접촉). 사용자가 요청에서 이를 알고 구현 전 계획을 이미 승인했으므로 경고만 기록하고 진행한다.
  • 경고(진행): 기존 DB 보정은 개발 DB 복사본으로만 확인하고 개발 DB(./data/battery)와 8080 서버는 건드리지 않는다.

2이해 점검 — 모르는 부분은 추측하지 않고 사람에게 확인을 요청해 주세요(HITL)

배경 · 사용자가 어떤 상황인가 이해함

지금 총 비용은 생산 원가와 운항비뿐이라 공장을 운영하는 비용이 계획 비교에 반영되지 않는다. 운영 담당자는 공장 4곳의 하루 운영비를 마스터에서 정하고, 주문일부터 그 공장의 마지막 수거일까지의 운영비가 총 비용에 들어가길 원한다.

근거

요청 문구, PRD 6장 비용과 일수, PRD 9장 공장 운영비, Planner.java toPlan(totalCost = 생산 원가 + 운항비), MasterService.initDefaults(운영비 없음).

목적 · 왜 필요한가 이해함

경로안 비교와 확정 주문의 총 비용이 공장 운영비까지 반영하게 한다. 비용 기준 안은 총비용 최소가 되고, 확정 주문은 확정 당시 운영비를 스냅샷으로 보존하며, 기존 주문은 그대로 열리고 운영비는 없음으로 보인다.

근거

PRD 9장(계산·경로안·화면·기존 주문), INTENT 8.4, 원칙 4(스냅샷)·7(전부 검증)·12(원 단위 정수).

3규모와 위험

변경 규모 (여러 계층, 많은 파일, DB 변경, 핵심 규칙 변경, 되돌리기 어려움 → 큼)

작음중간큼

사용자가 이 규모·위험을 알고 있는가: 예 — 요청에 "구현 전 계획은 사람이 이미 승인했다", 6가지 결정에 첫 실행 보정·마스터 버전 증가·스냅샷·기존 주문 처리가 들어 있다.

위험심각도대응
기존 DB(이미 행이 있는 Factory 테이블)에 컬럼을 추가할 때 실패하거나 값이 비어 앱이 깨진다높음nullable 컬럼으로 추가하고 첫 실행 때 비어 있는 곳만 10억으로 채우며 값이 있으면 덮어쓰지 않는다. 개발 DB 복사본으로 확인한다.
이전 형식 확정 주문(운영비 필드 없음)을 열면 화면이 깨지거나 애니메이션 총 비용이 어긋난다중간화면 JS가 필드 없음을 없음으로 표시하고 저장된 총 비용은 그대로 쓴다. planJson은 다시 쓰지 않는다. 기존 주문 없음 표시 테스트를 추가한다.
기존 E2E의 문구·표 순서·숫자 단언이 깨진다중간새 표는 맨 뒤에 두고, 문구·숫자만 새 규칙에 맞게 고쳐 확인 의도는 유지한다.
가장 빠르게와 총비용 최소가 같은 안이 되는 경우가 늘어 두 카드가 같아 보인다낮음같은 안일 때 안 카드 아래에 두 안이 같습니다 한 줄 안내를 보여 준다(사용자 결정).
운영비 입력값이 너무 커 계산 결과가 비현실적이거나 long 범위를 넘는다낮음하루 운영비 상한 1,000억 원 이하(사용자 결정)로 검증하고 상한 테스트를 둔다. 상한 x 운영 일수 x 4곳은 long 범위에 한참 못 미친다.

가정 (확인하지 못한 것)

  • Factory의 nullable 컬럼 추가가 기존 H2 파일 DB에서 실제로 되는지는 구현 때 개발 DB 복사본으로 확인한다(아직 확인하지 못함).
  • E2E-036~040이 입력칸을 읽어 되돌려 저장하는 방식이라 새 입력칸이 늘어도 영향이 작다고 추정한다(확인 필요).
  • 운영 일수의 끝은 그 공장의 마지막 수거일(배가 그 공장에 도착한 날)이다. 사용자가 확인했다.

R2경로안 비교에 운영비가 들어가고 비용 기준 안이 총비용 최소가 된다.
R3·R4확정할 때 운영비를 스냅샷에 담는다. 확정 주문은 확정 당시 값 그대로 보인다.
R5하루 운영비를 저장하면 마스터 버전이 올라 낡은 시뮬레이션은 확정할 수 없다.
R6상세에 운영비와 공장별 운영 일수가 보이고 기존 주문은 없음으로 보인다. 목록은 총 비용만 보인다.
R8·R9마스터에 공장별 하루 운영비 입력이 생기고, 0 초과 1,000억 원 이하 검증과 이유 모아 알림을 한다.
원칙 1세 안의 의미를 다시 점검하고 같은 안이면 화면에서 드러낸다.
원칙 2·6서버가 운영비까지 다시 계산한다. 일정·재고 시뮬레이션과 검산은 바꾸지 않는다.
원칙 3·4운영비를 바꾸면 버전이 오르고, 확정 스냅샷에 운영비를 담는다.
원칙 7·12·13운영비도 같은 검증 틀에 넣고 원 단위 정수로 다루며 마스터 데이터로 둔다.

단계내용
1Planner·Master·Plan: 나라별 마지막 수거일로 운영 일수를 구하고 운영비·총 비용을 계산한다. COST 선택 기준을 운항비+운영비 최소(동률은 소요 일수 짧은 안)로 바꾸고 이름을 총비용 최소로 바꾼다. FAST·NEAR는 그대로.
