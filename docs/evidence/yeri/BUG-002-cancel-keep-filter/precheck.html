1판단

버그로 확인되고 직접 재현했다. 취소 후 이동 주소가 /orders 로 고정돼 보던 필터가 풀린다. 변경은 작고 최소 수정이 가능해 GO.

이유

  • 현재 동작이 문서와 어긋남: 요구 문서(PRD 7장)의 "이전 페이지(주문 목록)"를 보던 화면으로 읽으면 필터가 유지돼야 하나, 현재는 항상 전체 목록이다. 필터 포함 여부가 문서에 명시되지 않았고 사용자가 "필터까지 포함"으로 정해 주었다(요구 변경이 아니라 모호한 문구의 확정).
  • 재현함: 포트 8099 별도 앱·메모리 DB에서 /orders?status=CONFIRMED 로 진입해 취소하자 http://localhost:8099/orders 로 이동했다.
  • 원인 확인: order-detail.js 취소 분기의 location.href = '/orders' 고정. 서버·DB 변경 없이 화면 스크립트와 문서·테스트만 바꾼다.

2이해 점검 — 모르는 부분은 추측하지 않고 사람에게 확인을 요청해 주세요(HITL)

배경 · 사용자가 어떤 상황인가 이해함

사용자가 확정 등 상태 필터를 건 주문 목록에서 주문 상세로 들어가 취소하면, 취소 후 필터가 풀린 전체 목록이 열려 보던 맥락을 잃는다.

근거

요청 문구, static/js/order-detail.js 취소 분기(location.href = '/orders'), 실제 재현(필터 주소 -> /orders).

목적 · 왜 필요한가 이해함

취소 직후 사용자가 보던 목록(필터 포함)으로 돌아가 이어서 작업하게 한다. 상세를 직접 열었다면 전체 목록. 문서의 "이전 페이지"가 이를 뜻하도록 명시한다.

근거

요청 문구, PRD.md 7장 "이전 페이지(주문 목록)", INTENT.md 9장 1번(BUG-001 해결 기술).

3규모와 위험

작음중간큼

사용자가 이 규모·위험을 알고 있는가: 해당 없음 — 큰 변경·높은 위험 없음. 서버·엔티티·상태 전이 변경 없음.

위험심각도대응
이동 주소를 이전 주소(referrer 등)에서 가져오므로 임의 주소로 이동(오픈 리다이렉트)중간같은 출처이고 경로가 정확히 /orders 일 때만 path+search 사용, 그 외는 /orders.
이전 주소를 못 얻는 경우(상세 직접 열기, 새로고침 등)낮음/orders(전체)로 대체. 기존 DEV-001 테스트가 이 경로를 지킨다.
취소 후 안내(1회 표시) 동작 회귀낮음flashMessage 로직은 그대로 두고 이동 주소만 바꾼다. 기존 안내 테스트가 지킨다.

가정 (확인하지 못한 것)

  • 이전 페이지는 document.referrer 로 얻는 것으로 가정. 목록이 주소를 sessionStorage 에 저장하는 방식도 가능하며 구현 단계에서 택한다(검증 기준은 같다).
  • 상세의 [목록으로] 링크(href="/orders")도 필터를 잃지만 이번 요청은 취소 직후 이동만 다룬다고 가정(별도 기록).
