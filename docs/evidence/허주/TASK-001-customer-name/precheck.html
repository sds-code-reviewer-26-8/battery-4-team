3규모와 위험

변경 규모 (여러 계층, 많은 파일, DB 변경, 핵심 규칙 변경, 되돌리기 어려움 → 큼)

작음중간큼

사용자가 이 규모·위험을 알고 있는가: 예 — "주문 시 입력 + 주문 이후 수정 + 완료/삭제 후 수정 불가"를 요청했고, Q1~Q4로 목록 열·문서 반영까지 정했다. 화면 3곳, API, DB 컬럼 1개가 닿는다.

위험심각도대응
화면에서만 수정 버튼을 숨기면 API 직접 호출로 완료 주문을 고칠 수 있다.높음서버(OrderService)에서 상태를 검사해 확정·진행이 아니면 BusinessException 으로 거부한다. 화면은 서버가 준 값만 보고 입력란을 보여 준다. 완료 상태 거부 테스트를 넣는다.
동시 수정: 검사와 저장 사이에 다른 사람이 완료로 바꾸거나 고객사를 바꿀 수 있다.중간changeStatus 처럼 화면 version 을 받아 비교하고, 저장 때 ObjectOptimisticLockingFailureException 을 409 충돌로 바꾼다(Order.java 56행 @Version).
입력 검증 누락(길이 초과, 공백만 입력, HTML 문자).중간서버에서 앞뒤 공백 제거, 빈 값은 null, 길이 초과는 400(메모와 같은 방식). 화면 출력은 esc() 사용.
기존 주문은 새 컬럼이 비어 있다. null 이 그대로 보일 수 있다.중간컬럼은 nullable 로 두고, 목록·상세에서 비어 있으면 "-" 를 표시한다(Q1). 개발 DB(./data/battery)는 건드리지 않고 테스트 DB 로만 확인한다.
고객사 수정도 version 을 올려, 상세 화면을 열어 둔 다른 사람의 상태 변경이 충돌(409)로 거부될 수 있다.낮음기존 충돌 안내 문구를 그대로 쓴다. 수정 성공 뒤 화면을 다시 불러 새 version 을 받는다.
고객사를 스냅샷(planJson)에 넣으면 원칙 4(확정 시점 값 보존)와 수정 가능성이 부딪친다.낮음고객사는 Order 컬럼으로만 두고 StoredPlan 은 건드리지 않는다. 문서에 "보존 대상이 아님"을 적는다.
E2E-023 이 목록 머리글 8개를 비교하므로 열을 추가하면 반드시 실패한다.중간같은 작업에서 E2E-023 의 기대를 9개(끝에 "고객사")로 고친다.

가정 (확인하지 못한 것)

  • 해결됨(사용자 결정): 고객사 최대 길이는 100자(앞뒤 공백 제거 후). 오류 문구는 "고객사 이름은 100자 이하로 입력하세요".
  • 해결됨(사용자 결정): 수정은 주문 작성자만 가능하다. 작성자가 아니면 "주문을 작성한 사람만 고객사를 수정할 수 있습니다"로 거부한다. 이전 가정("로그인한 누구나")은 폐기.
  • 가정: 수정 API 는 POST /api/orders/{id}/customer (본문: customerName, version). 취소된 주문은 행이 삭제되어 "주문을 찾을 수 없습니다"(400)로 막힌다. 이 동작은 구현 후 테스트로 확인한다.
  • 확인하지 못함: 개발 DB 의 실제 컬럼 추가 결과(ddl-auto=update 로 nullable 컬럼이 붙을 것으로 보지만 직접 실행하지 않음). 테스트 DB 가 인메모리 create-drop 이라는 점도 이번에 파일을 열어 확인하지는 않음.

범위 밖 확정 (PRD 10장) 저촉 여부

저촉함 (1건): PRD.md 130행 "계정 관리와 역할별 권한, 보안 요건, 확정 후 주문 수정, 다국어·통화 변환. 이번 범위에서 제외한다." 고객사 이름 수정은 확정 후 주문 수정에 해당한다. 같은 내용이 INTENT.md 128행에도 있다. 처리: Q4에 따라 코드보다 먼저 두 문서를 고쳐 "확정 후 주문 수정은 제외, 단 고객사 이름은 확정·진행 상태에서 수정 가능"으로 좁힌다. 나머지 10장 항목 중 "외부 시스템 연동, 결제, 정산"(121행)은 고객사가 단순 텍스트 입력이면 저촉하지 않는다(PRD 10장을 직접 열어 확인함). 고객사 마스터 관리·고객사별 정산은 범위 밖이라고 한 줄 추가한다.
