1판단

GO. 배경·목적이 분명하고 문서 규칙과 충돌하지 않는다. 다만 member 테이블에 컬럼이 추가되므로 구현 후 사람의 결과 확인이 필요하다.

이유

  • 요청이 현재 코드의 한계를 구체적으로 짚었다: MemberService.ITERATIONS 상수(65536)와 Member 엔티티에 해시 파라미터 필드 없음 (MemberService.java 25행, Member.java 20~30행).
  • 2번은 INTENT 3장 원칙 10, 9장 5번(로그인 흐름 테스트 얇음)을 직접 겨냥하며 문서 방향과 일치한다. 현재 OrderFlowTests 는 ("a!","abc") 한 건만 검증한다 (OrderFlowTests.java 107행).
  • application.properties 의 ddl-auto=update 라 컬럼 추가는 자동 반영되지만, 기존 행이 있는 H2 파일 DB(./data/battery)에 NOT NULL 컬럼을 넣으면 실패할 수 있다. 그래서 새 컬럼은 nullable 로 두고 null 은 기존 방식(PBKDF2WithHmacSHA256, 65536)으로 해석한다.

2이해 점검

배경 이해함

회원 가입 기능이 막 들어갔고(TASK-001, 002) 회원이 늘기 전이다. 해시 반복 횟수가 코드 상수라 올리면 기존 비밀번호가 모두 틀어진다.

근거

요청 1번, MemberService.java, Member.java, git log b1e6cbf

목적 이해함

회원별로 해시 파라미터를 저장해 반복 횟수를 나중에 안전하게 올릴 수 있게 하고, 가입 규칙 경계를 테스트로 고정한다.

근거

요청문, INTENT 원칙 10, INTENT 9장 5번

3규모와 위험

작음중간큼

사용자가 이 규모·위험을 알고 있는가: 예 — "가입 회원이 늘기 전에 파라미터를 저장 값에 함께 넣어 두면"

위험심각도대응
기존 회원(컬럼 추가 전 가입자)의 로그인 불가중간새 컬럼 nullable, null 이면 65536·PBKDF2WithHmacSHA256 으로 검증. 기존 회원 로그인 테스트(null 행)를 추가한다.
ddl-auto=update 로 개발 DB 스키마가 바뀜 (컬럼 추가)중간nullable 컬럼 추가만 하며 삭제·변경 없음. 되돌리려면 컬럼 무시 가능.
반복 횟수를 이번에 올리면 테스트·로그인 지연낮음이번에는 현행 65536 을 유지한다. 올리는 일은 별도 결정(OWASP 최신 권고는 확인하지 못함).

가정 (확인하지 못한 것)

  • 반복 횟수 값 자체는 이번에 바꾸지 않는 것으로 해석했다(요청은 "나중에 올릴 수 있게" 저장 구조를 요구).
  • 로그인 성공 시 자동 재해시(업그레이드)는 요청에 없어 범위 밖으로 둔다.

3

확인 방법: ./gradlew test --tests 로 영향받는 클래스 실행, 엔티티 컬럼 정의 확인
