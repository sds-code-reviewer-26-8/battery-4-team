1한눈에 보기 — 세 단계에서 한 일

1Prepare

  • 공개 가입이 열린 뒤 남은 보안 지적 두 가지(요청 횟수 제한 없음, 로그인 시 세션 ID 미재발급)를 해결한다.
  • 로그인 처리 코드(INTENT 원칙 14)와 보안 범위 문서를 바꾸는 위험한 변경. 로그인 한도가 정상 사용과 E2E에 영향을 줄 수 있음.
  • IP별 인메모리 제한기, 세션 ID 재발급, 테스트, 문서 갱신 순서. 체크리스트는 한도 초과 429, 세션 ID 변경, 기존 흐름 유지 3개.

2Implement

  • 가입(시간당 10회)·로그인(분당 60회)을 IP별로 제한해 초과하면 429, 로그인 성공 시 세션 ID를 새로 만든다.
  • 신규 파일 4개 포함 14개 파일(코드 5, 테스트·설정 7, 문서 2).
  • JUnit 전체와 login-access E2E 통과.

3Verify

  • 체크리스트 3개 모두 충족(직접 실행).
  • JUnit 36/36, E2E login-access 8/8 통과.
  • 사람 확인 필요 항목 있음(남은 이슈 참조).

2체크리스트 3개 결과

1
같은 IP에서 가입·로그인 한도를 넘기면 429와 이유 메시지가 오고, 한도 이내 요청은 기존처럼 성공한다 충족
근거: RateLimitTests 3건(가입 두 번 뒤 세 번째는 429와 Retry-After와 안내 문구, 다른 주소는 통과, 로그인은 가입과 따로 제한)과 RateLimitWiringTests 1건(app.rate-limit.* 설정값이 실제 앱에서 한도로 적용됨) 통과, OrderFlowTests 16건 통과(한도 안의 가입·로그인), E2E-043 통과(429 응답의 이유가 로그인·가입 화면에 보임). 기본값(가입 10회/시간, 로그인 60회/분)은 application.properties에 명시했다. 참고: 이 PC에서 PBKDF2 1회는 평균 62ms(100회 측정, 중앙값 61ms, p95 76ms, 8코어)여서 한 주소당 최대 부담은 로그인 약 3.7초/분, 가입 약 0.6초/시간이다.
2
로그인 성공 전후로 세션 ID가 달라지고 로그인 상태(/api/me)는 유지된다 충족
근거: OrderFlowTests.loginReplacesSessionIdOnlyOnSuccess 통과(로그인 뒤 ID 변경, /api/me 200, 실패한 로그인은 ID 불변). E2E-044 통과(실제 서버에서 JSESSIONID 쿠키 값이 바뀌고, 로그인 전의 쿠키로 /api/me를 부르면 401). changeSessionId() 호출을 끄면 E2E-044가 실패하는 것도 확인한 뒤 복원했다.
3
기존 로그인·접근 통제 흐름이 깨지지 않는다(admin 로그인, 가입 후 로그인, 401/redirect) 충족
근거: E2E login-access 8/8 통과(E2E-001~005, 042~044, 포트 8095, 메모리 DB), DemoApplicationTests 통과(컨텍스트 기동), JUnit 전체 36/36 통과.

★리팩토링 결과

  • 동작이 그대로임을 확인한 방법: 불변 목록(한도 안의 가입·로그인 응답, 검증 메시지, admin/admin 로그인, 로그아웃·/api/me, 401/redirect)을 JUnit 전체 36건과 E2E login-access 8건으로 확인. 의도된 동작 변화는 가입·로그인 한도 초과 시 429와 로그인 성공 시 세션 ID 변경 두 가지(precheck에서 승인 대상으로 명시).
  • 정리한 것: 제한 로직을 RateLimiter 한 클래스와 인터셉터로 분리해 컨트롤러는 세션 ID 재발급 한 줄만 추가.
  • 손대지 않은 것: CSRF 방어, 로그인 실패 계정 잠금, admin 하드코딩 제거, 다중 서버 공유 제한, 프록시 헤더 신뢰, 비밀번호 정책.
