GO. 요청의 배경과 목적이 분명하고, 사용자가 문서의 보안 범위 제외 방침을 알고 후속 보강으로 요청했다. 문서 갱신을 함께 계획에 넣는다.

이유

  • 요청문이 위치(AuthController.signup/login, MemberService), 위험(CPU 부담, 회원 행 증가, 세션 고정), 해결 방향(IP·시간당 제한, changeSessionId/재생성)을 구체적으로 적고 있다. 근거: 요청문, AuthController.java 47행(session.setAttribute만 호출), MemberService.java ITERATIONS=65536.
  • 현재 코드에는 횟수 제한도 세션 ID 재발급도 없음을 직접 확인했다(src/main grep에서 RateLimit, changeSessionId, 429 없음).
  • INTENT.md 7장 "보안 요건(CSRF 방어 등) 이번 범위에서 제외", 4장 "요구사항에 없는 범위 확장을 섞지 않는다(필요하면 먼저 PRD.md에 반영)", PRD.md 10장 범위 밖과 맞닿아 있다. 다만 INTENT 9장 3번이 공개 가입 위험을 이미 후속 확인 대상으로 적고 있고, 사용자가 이를 알고 보강을 요청했으므로 HILP 없이 진행하되 PRD/INTENT를 함께 고친다.
  • 요청은 "리팩토링"으로 지정됐지만 실제로는 동작이 바뀐다(가입 과다 요청 429, 세션 ID 변경). 사용자가 Loop를 지정했으므로 따르되, 불변 목록은 "정상 가입·로그인의 응답과 화면 흐름"으로 한정한다.

2이해 점검

배경 · 사용자가 어떤 상황인가 이해함

공개 회원 가입이 도입돼(커밋 bd0ab7f) 누구나 가입해 admin과 같은 권한을 얻는다. 가입·로그인 API는 인증 없이 열려 있고, 로그인은 기존 세션에 사용자만 넣는다.

대량 가입 요청으로 CPU와 DB 행이 소모되는 것을 막고, 로그인 시 세션 ID를 새로 발급해 세션 고정 공격을 막는다. 정상 가입·로그인은 그대로 동작해야 한다.

근거

3규모와 위험

변경 규모

작음중간큼

사용자가 이 규모·위험을 알고 있는가: 예 — 요청문이 위험 항목과 영향(보안 범위, 이전부터 있던 코드)을 직접 설명함

위험심각도대응
E2E·JUnit이 같은 IP(127.0.0.1)에서 로그인·가입을 반복해 제한에 걸려 기존 테스트가 깨질 수 있다.중간가입(시간당 10회)과 로그인(분당 60회)은 둘 다 application.properties 설정값으로 두고, 로그인은 정상 사용에 영향이 없도록 더 큰 한도를 쓴다. 테스트·E2E 실행 때는 설정으로 한도를 풀어 두고(테스트 프로퍼티, E2E 앱 실행 인자), 제한 동작 전용 테스트만 낮은 한도를 쓴다.
프록시 뒤에서 IP를 잘못 읽거나 메모리 맵이 무한히 커질 수 있다.중간request.getRemoteAddr()만 사용(프록시 헤더 불신뢰, forward-headers 설정 없음 확인). 만료 항목 정리로 맵 크기를 제한한다. 단일 서버 메모리 방식이라 다중 인스턴스에서는 공유되지 않음을 문서에 남긴다.
세션 재발급 시 로그인 상태가 풀리거나 속성이 사라질 수 있다.중간기존 세션이 있으면 changeSessionId()로 ID만 바꾸고 속성 유지, 없으면 새 세션 생성. 신규 JUnit과 E2E-001~005로 확인.
인증 코드(원칙 14)와 보안 범위 문서를 바꾸는 핵심 규칙 변경이다.중간구현 후 사람이 report.html을 확인한다.

가정 (확인하지 못한 것)

  • PBKDF2 CPU 부담 수치는 요청문 그대로 추정이며 측정하지 않았다.
  • IP당 한도 수치는 요청에 없어 기본값을 정해 설정으로 뺀다: 가입 시간당 10회, 로그인 분당 60회(로그인은 정상 사용에 영향이 없도록 더 크게 잡음). 값은 설정으로 바꿀 수 있고 report에 기록한다.
  • 외부 보안 라이브러리(Spring Security 등)는 추가하지 않고 서블릿·서비스 코드로 구현한다고 가정했다. 빌드 파일(pom/gradle)은 Glob 결과에 없어 확인하지 못했다.
