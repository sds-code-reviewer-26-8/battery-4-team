구현 전 점검

Master.days()가 항로 목록(routes)을 호출할 때마다 처음부터 찾는다. 항로를 조회용 표(Map)로 만들어 두고 거기서 바로 꺼내도록 바꿔, 같은 결과를 더 간단히 얻게 한다. 계산 결과·오류 메시지·화면·저장 형식은 한 글자도 바뀌면 안 된다. (REFACTOR-001 master-days)

날짜 2026-10-21 17:05:21회차 1작성 prepare 에이전트브랜치 feature/battery-hyemiJung4 · 커밋 a0ac971 (기준선 기록값; 작성 시점 HEAD 는 e838460)요청자 정혜미로그 해당 없음

1판단

진행 가능한 순수 리팩토링이지만, 안전망을 먼저 보강하려면 테스트 파일 1개를 추가해도 되는지 사람의 답이 필요하다 (needs-clarification).

이유

  • 문서 규칙과 blocking 충돌은 없다. 주의(caution) 3건뿐이다: Master 는 StoredPlan 에 담겨 planJson 으로 저장되므로 Map 이 JSON 에 새면 저장 형식이 바뀐다(원칙 4), 중복 항로는 첫 항목 우선이고 오류 메시지는 그대로여야 한다(원칙 6·8), 조회표는 Master 인스턴스에서 파생된 값이어야 한다.
  • 변경 대상은 src/main/java/com/example/demo/simulation/Master.java 한 파일이다(Node B). 기존 JUnit 22건과 E2E 45건은 기준선에서 모두 예상대로 통과했다(unit 22/22, E2E 45/45, 알려진 결함 3건 E2E-013b·033·035 는 test.fail 로 실패가 정상).
  • 안전망 구멍이 크다. days() 를 직접 검사하는 테스트가 없고, 항로 누락 메시지·역방향·a==b·중복 항로(첫 항목 우선)·Master JSON 모양이 어떤 테스트에도 고정돼 있지 않다(Node B gaps). 그래서 계획 맨 앞에 안전망 보강 단계를 둔다.
  • 직접 테스트를 넣으려면 허용 파일(Master.java 와 증거 폴더)을 벗어나 새 테스트 파일이 필요하다. 충돌하면 더 안전한 쪽을 택한다는 규칙에 따라 사람에게 먼저 묻는다.

⚠ 경고

  • Map 을 record 컴포넌트나 public 접근자로 두면 planJson 과 /api/master 응답에 항로 표가 섞이고, 과거 주문 스냅샷 읽기와 new Master(...) 호출부(BatteryService:100, PlannerTest:18)가 깨질 수 있다. 가장 큰 위험이다.
  • 단순 put 이나 toMap 으로 만들면 중복 항로에서 마지막 항목이 이기거나 중복 키 예외가 난다. 첫 항목 우선(putIfAbsent)을 지켜야 한다.
  • 항로가 10개뿐이라 성능 이득은 거의 없다. 이 변경의 가치는 코드 단순화이며, 성능 개선으로 설명하면 안 된다.
  • 정리 필요: 기준선 작업 중 잘못된 경로 입력으로 의도하지 않은 폴더 C:/c (하위에 docs/evidence/정혜미/REFACTOR-001-master-days/e2e-result.json)가 만들어졌다. 안전 검사에 막혀 지우지 못했으니 사용자가 C:\c 폴더를 직접 삭제해야 한다.

사용자에게 확인할 질문

  • days() 동작을 고정하는 작은 JUnit 테스트(예: src/test/java/com/example/demo/simulation/MasterTest.java)를 새로 추가해도 되는가? 안 된다면 특성 확인(characterization)은 증거 폴더에만 남기고 테스트는 추가하지 않는다.
  • routes 에 같은 구간이 두 번 있으면 지금처럼 목록의 첫 항목이 이기는 것으로 보존해도 되는가? DB 에 중복이 실제로 들어올 수 있는가(확인하지 못함)?
  • 조회표를 Master 안(지연 생성 또는 비직렬화 보관)에 두는 것으로 해도 되는가? 호출하는 쪽(Planner 등)으로 옮기는 안은 범위를 넓혀 채택하지 않는다.
  • 결과를 feature/battery-hyemiJung4 에 커밋할 것인가, 작업 폴더에만 남겨 검토할 것인가? (이번 단계에서는 commit·push 를 하지 않는다.)

2이해 점검 — 모르는 부분은 추측하지 않고 사람에게 확인을 요청해 주세요(HITL)

배경 · 사용자가 어떤 상황인가 이해함

Master.days(a, b) 는 호출마다 routes 목록을 스트림으로 처음부터 훑어 두 나라 사이 항로를 찾는다. Planner 가 정렬·순회·일정 계산에서 이 메서드를 자주 부른다.

근거

요청 문구, Master.java days() 21~30행, Node B 호출처 목록(Planner 134·230·233·258·312·316행)

목적 · 왜 필요한가 이해함

항로를 Map 으로 한 번 만들어 두고 바로 꺼내 코드를 단순하게 한다. 끝난 뒤에도 계산 결과, 오류 메시지, 화면, 저장 형식은 한 글자도 달라지면 안 된다.

근거

요청 문구 "같은 결과를 더 간단히", "한 글자도 바뀌면 안 된다"

3규모와 위험

변경 규모 (여러 계층, 많은 파일, DB 변경, 핵심 규칙 변경, 되돌리기 어려움 → 큼)

작음중간큼

사용자가 이 규모·위험을 알고 있는가: 예 — "한 글자도 바뀌면 안 된다"고 불변 조건을 직접 밝혔다. 규모는 파일 1개·메서드 1개로 작다.

위험심각도대응
Map 이 JSON(planJson, /api/master)에 새어 저장 형식이 바뀐다 / 과거 스냅샷을 못 읽는다높음record 컴포넌트·생성자 시그니처·public 접근자를 추가하지 않는다. 변경 전후 Master JSON 을 바이트 단위로 비교하고, 옛 planJson 이 읽히는지 확인한다.
중복 항로에서 첫 항목 우선이 마지막 우선으로 바뀐다중간putIfAbsent 로 구성한다. 중복 항로 사례를 변경 전에 기록해 두고 변경 후와 비교한다.
오류 메시지 "항로 정보가 없습니다: a-b" 가 달라진다 (인자 순서가 정규화됨)중간메시지는 호출자가 준 (a, b) 순서의 열거형 이름으로 만든다. 키 정규화가 메시지로 새지 않게 한다. 직접 단언하는 확인을 추가한다.
record 의 equals/hashCode/toString 이 바뀌거나, 공유 Master 에서 가변 캐시가 스레드 안전하지 않다중간조회표는 routes 에서 파생된 불변 값으로, 인스턴스 단위로만 보관한다. 정적 캐시는 쓰지 않는다. 동등성 비교에 끼지 않게 한다.
테스트가 얇아 같은 결과인지 알아채지 못한다중간변경 전에 5개국 모든 순서쌍 days 값을 기록한다(특성 확인). 안전망 보강을 맨 앞 단계로 둔다.

가정 (확인하지 못한 것)

  • 실습용 시스템이라 데이터가 불완전할 수 있다. DB 의 routes 에 중복 항로가 들어올 수 있는지는 확인하지 못했다(유니크 키가 있을 것이라는 추측일 뿐이다).
  • Jackson 3(tools.jackson)이 record 를 직렬화·역직렬화하는 세부 규칙(비컴포넌트 필드나 접근자가 JSON 에 나타나는지)은 코드로 직접 확인하지 못했다. Node A·C 의 설명에 따른다. 변경 후 실제 JSON 비교로 확인해야 한다.
  • PRD·INTENT 는 작업 폴더에 로컬 파일(PRD.local.md, INTENT.local.md)로만 있고, 아래 R·원칙 번호는 Node A 의 인용과 템플릿 목록을 따른 것이다. 문서 버전은 확인하지 못했다.
  • 작성 시점 HEAD(e838460)와 기준선에 기록된 커밋(a0ac971)이 다르다. 그 사이 Master.java 가 바뀌었는지는 확인하지 못했다(현재 파일은 읽어 확인했고 Node A·B 의 설명과 같다).
  • 개발 앱(8080)과 개발 DB 는 건드리지 않았다. 기준선 검증은 8081·메모리 DB 로만 했고 8081 은 종료했다. 이번 prepare 에서는 앱을 새로 띄우지 않았다.

테스트 공백

  • 항로 누락 오류 메시지("항로 정보가 없습니다: A-B", 인자 순서 포함)를 확인하는 테스트가 없다.
  • 역방향 조회와 a==b(0)를 days() 로 직접 확인하는 테스트가 없다.
  • 중복·양방향 항로에서 첫 항목 우선인지 고정하는 테스트가 없다.
  • Master JSON 직렬화와 planJson 왕복(필드 집합, 동등성)을 정확히 비교하는 테스트가 없다.
  • Master equals/hashCode/toString, factory() 오류 메시지를 확인하는 테스트가 없다.
  • 5개국 25개 쌍 전체의 days() 값(골든 값)이 없다. 한 쌍만 잘못 매핑돼도 PlannerTest 가 놓칠 수 있다.
  • 공유 Master 의 동시 호출 안전성과 조회 성능은 테스트도 측정도 없다(확인하지 못함).

7구현 계획

단계내용
0(질문 답을 받은 뒤) 기준선 확인: 현재 커밋을 기록하고 기존 테스트 결과를 증거 폴더에 "변경 전"으로 저장한다. 이미 실패하는 것이 있으면 멈추고 보고한다. (기준선 unit 22/22, E2E 45/45 는 이미 기록돼 있고 작업 시점에 다시 확인한다.)
1안전망 먼저 보강(맨 앞): 변경 전 코드에서 days() 를 5개국 모든 순서쌍(a==b 포함), 중복 항로(첫 항목 우선), 누락 항로 메시지, Master JSON 샘플, Master equals/toString 으로 확인해 증거 폴더에 저장한다. 사용자가 승인하면 같은 내용을 MasterTest.java 로 만들어 변경 전 코드에서 통과하는 것을 확인한다. 승인하지 않으면 테스트 파일은 만들지 않고 증거 폴더 기록만으로 간다.
2변경: Master.java 만 고친다. routes 에서 나라 쌍(방향 무관 키)으로 조회표를 만들되 putIfAbsent 로 첫 항목이 이기게 한다. days() 는 a==b 이면 0, 조회표에서 찾고, 없으면 기존과 같은 메시지의 IllegalStateException 을 던진다. 조회표는 record 컴포넌트·public 접근자가 아니고 JSON 에 나타나지 않으며(필요할 때만 @JsonIgnore), 불변이고 인스턴스 단위(정적 캐시 아님)이며 equals/hashCode 에 끼지 않는다.
3생성 방식 결정: 조회표를 지연 생성할지 생성 시점에 만들지 정하되, 기존 public 생성자 시그니처와 옛 planJson 역직렬화(Jackson 3 의 생성자 선택)가 바뀌지 않게 한다. 두 번째 생성자는 추가하지 않는다. routes() 목록은 변경하지 않는다.
4검증: 단계 1 과 같은 확인을 다시 실행해 결과가 글자 단위로 같은지 비교하고, Master JSON 샘플이 바이트 단위로 같고 옛 planJson 이 읽히는지 확인한다. JUnit 전체와 E2E(8081, 메모리 DB)를 다시 실행해 기준선과 같은 결과인지 본다.
5범위 확인: git diff --stat 으로 Master.java(와 승인된 MasterTest.java), 증거 파일만 바뀌었는지 확인하고 diff 와 전후 비교를 증거 폴더에 저장한다. PRD.local.md 등 로컬 미추적 파일은 포함하지 않는다.
6결과 메모를 증거 폴더에 짧게 쓴다(무엇을 바꿨나, 무엇을 비교했나, 결과). 요청이 없으면 commit·push 를 하지 않는다.

HITL이면 계획은 비워 두셔도 됩니다. 사용자의 답을 받은 뒤 다시 점검하겠습니다. (위 계획은 답을 받은 뒤 그대로 진행할 초안입니다.)
