1한눈에 보기 — 세 단계에서 한 일

판정: 통과하지 못함(3/3회 시도). 빌드·단위 테스트·E2E·전후 사진 비교는 모두 기대대로였지만, 승인된 계획(조회표를 Master 인스턴스 안에 둔다)을 지키지 못하고 정적 캐시로 대체했기 때문에 사람의 확인이 필요합니다.

1Prepare

  • days() 의 선형 탐색을 나라 쌍 조회표로 바꾸되 동작은 한 글자도 바꾸지 않는 리팩토링.
  • 경고: 계획이 Master 인스턴스 안의 조회표를 요구하지만, record 는 인스턴스 필드를 가질 수 없고 같은 계획이 컴포넌트·접근자·생성자 추가를 금지해 서로 모순됨.
  • 계획 4단계(안전망 → Master.java 변경 → 전체 검증 → 발견 사항은 보고만). 허용 파일은 Master.java 와 MasterTest.java 두 개.

2Implement

  • days() 가 방향 무관 나라 쌍(PairKey) 조회표를 쓰도록 변경. 조회표는 Master 값별 정적 WeakHashMap 캐시에 보관(계획과 다름).
  • 2개 파일: Master.java(수정), MasterTest.java(신규 테스트).
  • 변경 전 코드에서 MasterTest 통과 확인, 변경 후 ./gradlew test 전체 통과.

3Verify

  • 체크리스트 3개 중 2개 충족, 1개 미충족(계획 준수).
  • JUnit 28/28 통과. E2E 정상 통과 42 + 알려진 결함 3(예상대로 실패), 예상 밖 결과 0.

  • 동작이 그대로임을 확인한 방법: MasterTest 6개(변경 전 코드에서 먼저 통과), JUnit 28/28, E2E 45건 모두 기대대로, 전후 사진 13개 값 동일. 단, 계획 제약 일부를 지키지 못했으므로 "완전한 통과"로 보지 않음.
  • 정리한 것: days() 의 선형 탐색을 조회표 조회로 바꿈. 다만 정적 캐시와 PairKey 가 늘어 코드는 오히려 길어졌고(+30 −5), "더 간단히"라는 목적을 달성했는지는 사람이 판단해야 함.
  • 손대지 않은 것: Master.factory() 의 선형 탐색, Planner, 화면·저장 형식, 기존 테스트.

5회차 이력

  • 1회차 — FAIL (1단계만 완료하고 멈춤)
    MasterTest 를 만들고 변경 전 코드에서 통과를 확인했으나, record 가 인스턴스 필드를 가질 수 없어 계획 2단계를 구현하지 못했다. Master.java 는 수정하지 않았다. 빌드·단위 28/28, E2E 45건은 기대대로였고 사진은 코드가 안 바뀐 상태에서 같았다.
  • 2회차 — FAIL (구현 없음)
    같은 모순 때문에 Master.java 를 바꾸지 않았다. 수정된 계획의 승인이 전달되지 않았고, 대안(정적 캐시 / class 전환 / 현행 유지)을 임의로 고르지 않았다. 사진 단계에서도 추적 파일 변경이 없다고 경고했다.
  • 3회차 — 검증은 모두 통과했으나 최종 판정은 "통과하지 못함"
    "모두 권장대로 진행해줘"를 정적 캐시(WeakHashMap) 승인으로 해석해 구현했다(구현자의 해석이며, 사용자가 정적 캐시를 명시적으로 승인했는지는 확인하지 못함). 빌드 28/28, E2E 45건 기대대로, 사진 13개 동일, 범위 대조 이상 없음. 계획과 다른 구현이라 사람에게 넘김.

6남은 이슈 · 확인하지 못한 것

계획과 다르게 한 것

  • 계획 2단계의 "Master 인스턴스 안 조회표"는 record 제약상 불가능해 정적 캐시로 구현함. 이 방식의 채택 승인이 필요함. 다른 선택지: record 를 class 로 바꾸기(접근자·Jackson·equals 영향 검토 필요) 또는 현행 유지.

구현 중 발견했지만 고치지 않은 것 (foundIssues)

  • 정적 캐시의 키가 Master 자체라서 days() 를 부를 때마다 Master 의 hashCode(factories, routes 전체 해시)를 계산한다. 항로가 10개뿐이라 기존 스트림 탐색과 비슷한 비용일 수 있고, 성능 개선 효과는 측정하지 않아 확인하지 못함.
  • routes 가 변경 가능한 List 라면 생성 뒤 내용이 바뀔 때 WeakHashMap 키의 해시가 어긋나 캐시가 틀릴 수 있다. 현재 코드는 routes 를 바꾸지 않지만 보장 장치는 없다. 후속으로 routes 불변 복사 또는 class 전환을 검토할 수 있음.
  • Master.factory() 도 호출마다 스트림으로 선형 탐색한다. 이번 범위 밖이라 고치지 않음.
  • 중복 항로가 있어도 오류 없이 첫 항목이 쓰인다. 현재 동작이며 MasterTest 가 고정함.
  • MasterTest.java 는 git 에 추적되지 않는 상태(untracked)이며, 계획대로 commit 하지 않았음.

확인하지 못한 것

  • 정적 캐시가 동시 호출에서 안전한지 별도 테스트로는 확인하지 못함(synchronized 로 보호했다는 코드 읽기 근거만 있음).
  • 성능 개선 여부(측정 없음).
  • E2E 의 흐름별 건수(집계 없음).
  • 사용자가 "권장대로"로 정적 캐시를 의도했는지.
  • 시도 3의 최종 MasterTest 가 변경 전 코드에서 6개 모두 통과했는지: 변경 전 확인 기록은 5개 통과로만 남아 있음.
