# 영은의 Loop 설계 (`/work-loop`)

battery 프로그램에 **구현 요청**을 처리하는 Loop입니다. Dynamic Workflow로 만들었고, `/work-loop <구현할 내용>`으로 시작하고, 사람이 계획을 승인한 뒤 `/work-loop 승인 <작업 폴더>`로 이어서 실행합니다. 위험한 변경이면 결과 확인 뒤 `/work-loop 확정 <작업 폴더>` 또는 `/work-loop 수정 <작업 폴더> <수정 내용>`으로 마무리합니다.
이 문서는 설계를 설명합니다.

## 1. 한 줄 설명

요청을 받으면 **먼저 점검**(prepare)하고, 사람이 계획을 **승인**하면 **구현**(implement)한 뒤, **검증**(verify)합니다. 검증에 실패하면 verify가 **단순 실패**(구현이 기준을 못 맞춤)와 **방향 문제**(계획·체크리스트·요청 이해가 틀림)로 나눠, 단순 실패는 **구현으로**, 방향 문제는 **점검 단계로** 되돌아가 다시 시도하고, 통과하면 보고서를 남기고 끝납니다.

## 2. 흐름

```
 /work-loop <구현할 내용>                          ← 첫 번째 실행
  ▼
┌─► [prepare]   배경·목적 / 문서 규칙 / 규모·위험 점검 ──► precheck.html
│     │         체크리스트 3개, 바꿀 파일 목록
│     ├─ HILP ──► ★ 종료 (사람에게 질문·경고를 돌려줌)
│     ▼ GO
│    ★ 계획 승인 대기 ──► 종료 (승인 전에는 코드를 바꾸지 않음)
│     ▼
│   사람이 precheck.html 확인
│     ▼
│  /work-loop 승인 <작업 폴더>                       ← 두 번째 실행
│     ▼
│ ┌► [implement] 승인된 계획 범위 안에서 Plan → 구현 → 자가검증
│ │   ▼
│ │ [verify]    체크리스트·테스트·Lint·문서 규칙 확인
│ │   ├─ PASS ──► report.html 작성 ──► ★ 종료
│ │   │            └ 위험한 변경이면 ★ 사람 결과 확인 대기 (awaiting-result-review)
│ │   │                 ├ /work-loop 확정 <작업 폴더>        → 확정, 끝
│ │   │                 └ /work-loop 수정 <작업 폴더> <내용>  → implement 로 돌아가 수정 반영 → verify
│ │   ▼ FAIL (최대 3라운드)
│ │   ├─ 단순 실패 ─► implement로 (계획·체크리스트 그대로, 그 문제만 고침)
│ └───┘
└─────── 방향 문제 ─► prepare로 (실패 내용을 들고 다시 점검)
                      └ 새 계획이 승인된 범위를 벗어나면 ★ 다시 승인 대기
```

## 3. 단계별로 하는 일

### prepare (구현 전 점검)
코드는 건드리지 않고 점검만 합니다. 다음을 확인합니다.

1. **배경 이해** — 사용자가 어떤 상황인지 이해했는가
2. **목적 이해** — 이 기능이 왜 필요한지 이해했는가
3. **문서 규칙 부합** — 요청이 `PRD.md`, `INTENT.md`의 규칙과 어긋나지 않는가
4. **규모와 위험** — 변경이 너무 거대하거나 심각한 위험이 있는데 사용자가 모르고 있지 않은가

하나라도 걸리면 추측으로 채우지 않고 `HILP`를 반환합니다. 문제가 없으면 `GO`와 함께 **구현 후 확인할 체크리스트 3개**, 구현 방향(brief), **바꿀 파일 목록**을 반환합니다. 이 계획이 사람이 승인하는 대상입니다. 요청의 Loop 종류(`integrate | develop | refactor | bugfix`)도 정해 템플릿의 `data-loop`에 씁니다.

### implement (구현)
승인된 계획(`precheck.html`)을 먼저 읽고, 코드를 수정하기 전에 **Plan**(목적, 관련 코드, 수정할 파일, 가정)을 세우고, 승인된 범위 안에서만 구현합니다. 범위를 벗어나야 하면 멈추고 보고합니다. 끝나면 **자가검증**(Plan 대조, 빌드·테스트 실행, `git diff` 확인)을 하고 결과를 보고합니다.

### verify (검증)
implement의 자가검증을 믿지 않고 직접 확인합니다.

1. prepare의 **체크리스트 3개**를 항목별로 확인
2. 관련 **테스트 실행** (Gradle, Playwright). E2E는 개발 서버(8080)·개발 DB가 아니라 별도 포트·별도 DB에서 돌림. 실행하지 못한 테스트는 통과로 치지 않음
3. **Lint** 실행. 오류가 있으면 FAIL
4. **문서 규칙 부합** 확인 (`PRD.md`, `INTENT.md`)

하나라도 어긋나면 FAIL, 모두 충족하면 PASS입니다.

## 4. 피드백 루프와 종료 조건

| 상황 | 동작 |
|---|---|
| verify **FAIL — 단순 실패** (`next: IMPLEMENT`) | **implement로 되돌아감**. 승인된 계획과 체크리스트는 그대로 두고, `issues`와 직전 구현 요약을 받아 그 문제만 고침 (테스트 실패·회귀, 새 테스트 누락, Lint 오류 등) |
| verify **FAIL — 방향 문제** (`next: PREPARE`) | `issues`와 직전 구현 요약을 들고 **prepare로 되돌아감**. 점검·체크리스트·brief를 다시 만듦. 새 계획이 이미 승인된 범위(목표·바꿀 파일)를 벗어나면 `awaiting-approval`로 종료해 다시 승인받음 (범위 밖 수정이 필요함, 체크리스트가 틀림, 요청 이해·문서 규칙 충돌, 큰 위험 발견, 같은 실패 반복 등) |
| prepare **GO** (첫 실행) | `awaiting-approval`로 **종료**. `precheckPath`, 계획, 체크리스트, 다음에 할 명령을 돌려줌 |
| verify **PASS** | `report.html` 작성 후 **루프 종료** (`passed`) |
| verify **PASS** + **위험한 변경** | `report.html` 작성 후 **`awaiting-result-review`로 종료**. 사람이 report를 확인하고 `/work-loop 확정`으로 확정하거나 `/work-loop 수정`으로 수정을 요청 |
| `/work-loop 확정 <작업 폴더>` | 결과 확인을 마쳤다고 `confirmed`로 종료. `report.html`과 코드는 건드리지 않음 |
| `/work-loop 수정 <작업 폴더> <수정 내용>` | prepare를 건너뛰고 승인된 계획 그대로 **implement부터** 수정 요청을 반영한 뒤 verify. 이후 흐름은 위와 같고, 다시 위험한 변경이면 결과 확인 대기로 끝남 (3라운드 상한 적용). 승인된 범위를 벗어나는 수정은 implement가 멈추고 보고 |
| prepare **HILP** | **루프 종료**. 사람이 답하거나 결정해야 다시 시작할 수 있음 |
| **3라운드** 안에 통과 못 함 | 조용히 넘어가지 않고 `failed`와 남은 문제를 결과에 명시하고 종료 |
| 단계가 중단됨 | `aborted`와 중단된 단계를 반환 |

## 5. Human-in-the-loop

사람이 끼어드는 지점은 세 곳입니다. 앞의 둘은 항상, 세 번째는 **위험한 변경일 때만** 적용됩니다.

1. **구현 전 계획 승인** — prepare가 GO를 반환하면 워크플로는 `awaiting-approval`과 함께 `precheckPath`, 계획, 체크리스트를 돌려주고 끝납니다. 사람이 `precheck.html`을 확인하고 `/work-loop 승인 <작업 폴더>`를 실행해야 구현이 시작됩니다. **승인 전에는 코드를 바꾸지 않습니다.**
2. **prepare가 HILP를 반환할 때** — `needs-human`과 함께 `question`, `warning`, `precheckPath`를 돌려주고 끝납니다. 사람은 `precheck.html`로 무엇 때문에 멈췄는지 확인하고, 답을 보태 `/work-loop`를 다시 실행합니다.
3. **구현·검증 후 결과 확인 (위험한 변경만)** — verify가 PASS해도 `awaiting-result-review`로 끝나, 사람이 `report.html`을 확인합니다. verify **전**이 아니라 **후**에 보는 단계입니다.
   - 문제가 없으면: `/work-loop 확정 <작업 폴더>` — 확정하고 끝
   - 고칠 것이 있으면: `/work-loop 수정 <작업 폴더> <수정 내용>` — 승인된 계획 범위 안에서 수정 반영 → verify, 다시 결과 확인

워크플로 안에서 사람을 기다릴 수 없어서 **두 번에 나눠 실행**합니다. 승인 실행은 prepare를 다시 하지 않고 승인된 `precheck.html`의 계획을 그대로 씁니다.

**결과 확인이 필요한 위험한 변경**(prepare가 판단, 사용자가 알고 요청했어도 해당)
- 변경 규모가 `큼`
- 심각도 `높음` 위험이 있음
- DB 스키마·데이터를 바꿈
- 핵심 불변식(확정 주문 불변, 상태 전이, 서버 재계산 등) 코드를 바꿈
- 되돌리기 어려운 변경(삭제, 대규모 이름·구조 변경 등)

해당하면 `precheck.html`의 "주의"에 `구현 후 결과 확인: 필요 — 이유`를 적고, 첫 번째 실행 결과에도 표시합니다. verify는 이 줄을 읽어 `resultReviewNeeded`로 반환하고, 검증 중 큰 위험이 드러나면 `true`로 올릴 수 있습니다. 해당하지 않으면 PASS와 함께 바로 끝납니다.

## 6. 산출물 (Evidence)

| 산출물 | 경로 | 만드는 단계 |
|---|---|---|
| 구현 전 점검 HTML (바꿀 파일 목록 포함, 사람이 승인하는 계획) | `docs/evidence/youngeun/{TASK-번호-작업명}/precheck.html` | prepare (HILP일 때도) |
| 구현 결과 보고 HTML | `docs/evidence/youngeun/{TASK-번호-작업명}/report.html` | verify (PASS일 때만) |

- 작업 폴더는 첫 prepare가 `TASK-001-bugfix` 같은 형식으로 정하고, 이후 라운드와 다른 단계가 **같은 폴더**를 씁니다.
- 두 HTML은 **팀 공통 템플릿**(`docs/templates/`)을 복사해 `{{...}}`를 채워 만듭니다. 원본 템플릿은 고치지 않습니다.
- FAIL이면 report는 만들지 않습니다. 실패 내용은 `issues`로 prepare에 전달됩니다.

## 7. 설계 결정

- **서브에이전트 분리**: 점검·구현·검증을 서로 다른 대화로 나눠, 구현한 쪽이 자기 결과를 그대로 승인하지 못하게 했습니다.
- **체크리스트 3개**: prepare가 구현 전에 "끝나면 무엇을 봐야 하는가"를 정해 두면, verify가 그 기준으로 확인합니다. 구현 후에 기준이 바뀌는 것을 막습니다.
- **실패를 둘로 나눠 회귀**: 단순 실패에 매번 prepare를 거치면 에이전트 호출이 늘고 체크리스트(검증 기준)가 라운드마다 바뀝니다. 그래서 구현이 기준을 못 맞춘 단순 실패는 implement로, 계획·체크리스트·요청 이해가 틀린 방향 문제만 prepare로 보냅니다. 판단이 서지 않으면 prepare로 보냅니다. 새 계획이 승인된 범위를 벗어나면 사람이 다시 승인해야 합니다.
- **구현 전 사람 승인**: 점검이 통과해도 사람이 계획을 보기 전에는 코드를 바꾸지 않습니다. 승인 없이 구현해 버린 시험 실행의 경험에서 넣었습니다.
- **라운드 상한 3회**: 같은 문제로 무한히 도는 것을 막고, 도달하면 결과에 드러냅니다.
- **확인하지 못한 것은 통과가 아님**: 실행하지 못한 테스트는 "미실행"으로 적고 통과로 치지 않습니다.
- **Report는 PASS일 때만**: 보고서가 통과 사실의 증거가 되도록 합니다.

## 8. 시험 실행 결과와 개선

두 가지 요청으로 시험 실행했고, 두 번 모두 바뀐 코드는 commit하지 않고 되돌렸습니다.

- **고객사 입력 추가**: 1라운드에서 17개 파일이 바뀌었고, verify가 기존 E2E가 깨진 것을 잡아 prepare로 되돌렸습니다. 사람이 2라운드 검증 도중 중단했습니다.
- **로그인 화면 문구 한 줄 추가**: 계획 승인에서 멈추고, 승인 후 1라운드 만에 PASS했습니다.

첫 시험에서 찾은 문제를 다음과 같이 Loop에 반영했습니다.

- **구현 전 계획 승인**: 사람이 계획을 보기 전에 코드가 바뀌던 문제를 막았습니다. (확인함)
- **바꿀 파일 범위 지정**: 계획의 파일만 바뀌고, 범위를 벗어나면 implement가 멈춥니다. (파일 한 개 수정은 확인, 범위를 벗어나는 경우는 아직 돌려 보지 않음)
- **실패 두 갈래 회귀**: 단순 실패는 implement로, 방향 문제는 prepare로 보냅니다. (가짜 에이전트로 흐름만 확인, 실제 실행은 모두 1라운드에 통과)
- **E2E는 별도 포트·DB에서 실행**: 개발 서버(8080)와 개발 DB를 건드리지 않습니다. (확인함)

**사용 규칙**: 워크플로 스크립트를 고친 직후에는 이전 버전이 돌 수 있습니다. 고친 뒤에는 인자 없이 실행해 사용법 문구가 새 버전인지 먼저 확인한 다음 실행합니다.
