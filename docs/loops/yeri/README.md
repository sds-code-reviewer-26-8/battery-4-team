# 예리의 Loop 설계

battery 프로그램의 **버그를 고칠 때**(버그수정)와 **새 기능을 추가할 때**(기능개발) 쓰는 Loop입니다.
Dynamic Workflow(`/ih`)와 Subagent(prepare, implement, verify)로 만들며, 이 문서에는 **설계 설명**을 적습니다.
요청 문장으로 유형을 자동으로 나누고, 같은 뼈대(prepare → implement → verify)에 **유형마다 점검·검증 방법만 달리합니다.**

## 1. 한 줄 설명

요청을 받으면 **먼저 점검**하고, 문제가 없으면 **구현**한 뒤, 보유한 **테스트를 모두 돌려 검증**해서 결과를 HTML 두 장으로 남깁니다. 검증에 실패하면 그 실패를 들고 **점검 단계로 되돌아갑니다.**

- **버그수정:** "이런 버그를 고쳐 주세요" → 재현·원인을 확인하고, 원인 한 곳만 최소로 고칩니다.
- **기능개발:** "이런 기능을 추가해 주세요" → 문서 근거와 영향 범위, 빠진 정보를 점검하고, **사람이 계획을 승인한 뒤** 계획대로 구현합니다.

## 2. 범위

- **버그수정:** 동작이 PRD·INTENT에 정한 것과 다르거나 오류가 나는 문제를 고치는 일
  (예: 취소 직후 삭제된 주문 상세로 이동해 HTTP 500이 나는 것, 없는 주문 번호로 접속하면 안내 없이 HTTP 500이 나는 것)
- **기능개발:** 문서(PRD 등)에 근거가 있는 새 기능이나 새 항목을 화면·API·DB에 더하는 일
  (예: 공장별 하루 운영비를 마스터에서 설정하고 총 비용에 반영하는 것, 주문에 필요 납기일을 저장하는 것)
- **다루지 않는 일:** 구조만 바꾸는 리팩토링, 여러 브랜치를 합치는 통합. 에이전트에는 유형별 규칙이 있지만 이 문서에서는 다루지 않습니다.
- **유형이 어긋나면:** 버그수정으로 들어왔는데 실제로는 기능 추가이거나(큰 변경·DB 스키마 변경 등), 그 반대이면 prepare가 `HITL`로 알립니다.
- 유형 표시는 산출물 HTML의 `<body data-loop="bugfix">` 또는 `data-loop="develop"`입니다. HTML 틀은 팀 공용 템플릿(`docs/templates/`)을 씁니다.

## 3. 흐름

```
 /ih 버그 설명
  ▼
[prepare]   배경·목적을 이해했나? 큰 변경·높은 위험을 사용자가 아나?
  │         재현·원인 확인, 구현 후 확인할 체크리스트 3개
  │         ──► 점검 로그 + precheck.html
  ├─ status HITL ─► Loop 종료 (사람에게 질문·경고를 돌려줌, 수정하지 않음)
  │                  기능개발은 구현 전 계획 승인 때문에 여기서 한 번 멈추는 것이 기본
  │                  (사람이 답·승인하면 /ih 를 다시 실행해 GO 로 이어 감)
  ▼ GO
[implement] Plan → 수정 → 자가검증
  ▼
[verify]    체크리스트 3개 확인 + 보유한 Regression Test 전부 실행
  │         ──► 검증 로그
  ├─ FAIL ─► 실패 내용과 피드백을 들고 prepare 로 되돌아감 (최대 3회차)
  ▼ PASS
 Report 작성 (report_*.HTML) ─► Loop 종료  (commit·PR은 사람이 직접)
```

각 단계는 Subagent라서 **새 대화로 시작**합니다. 앞 단계의 생각에 끌려가지 않아 오작동이 줄어듭니다.

## 4. 단계별로 하는 일

**유형별로 다른 점 한눈에 보기**

| 단계 | 버그수정 | 기능개발 |
|---|---|---|
| 1. 요청 판단 | 현재 동작이 PRD·INTENT가 정한 것과 **다른가**(버그인가). 정한 동작이 없거나 요구 변경이면 HITL | 문서(PRD 9장 등)에 **근거가 있는 새 기능인가**. 문서에 없거나 PRD 10장 범위 밖이거나 INTENT 원칙을 깨면 HITL. 필요하면 PRD 반영이 먼저 |
| 2. 점검 내용 | 재현 방법을 **실제로 재현**하고 원인 코드 위치, 같은 증상이 다른 곳에 있는지 | 인수 기준(R번호), 들어갈 위치, **영향 범위**(화면·API·DB·기존 테스트), **정해지지 않은 것**(기본값·기존 데이터 처리)을 질문으로 정리 |
| 3. 계획 | 원인 한 곳만 고치는 최소 수정 | 어떤 순서로 무엇을 바꿀지, **이번에 하지 않는 것**까지 적은 계획 |
| 4. 사람 확인 | 이해 못했거나 큰 변경·높은 위험을 모를 때만 멈춤. 평소엔 끝까지 돎 | **구현 전 계획 승인이 기본.** 질문이 있으면 답을 받은 뒤 GO. 큰 변경은 알고 승인했다는 기록을 남기고 진행 |
| 5. 구현 | 계획의 원인 수정만. 정리·포맷·리팩토링 금지 | **계획에 적힌 파일만** 고침. 계획에 없는 파일이 필요하면 멈추고 보고. 기존 테스트의 확인 조건은 느슨하게 만들지 않고 새 테스트를 추가 |
| 6. 체크리스트 ① | 재현 절차가 수정 후 기대 동작이 된다 | **인수 기준대로** 동작한다 (화면·API를 실제로 확인) |
| 7. 체크리스트 ② | 재발 방지 테스트가 있고 통과한다(`test.fail()` 제거) | **새 기능 테스트**가 있고 통과한다(기능을 직접 검증하는지, 잘못 만들면 실패하는지) |
| 8. 체크리스트 ③ | 기존 Regression Test 전체 | 기존 Regression Test 전체 |
| 9. 변경 범위 | 원인과 무관한 변경이 섞이면 FAIL | 계획에 없던 기능·PRD 범위 밖 변경이 섞이면 FAIL. 계획에 없던 변경은 report에 따로 적음 |
| 10. 통과 조건 | Regression 전체 통과 | Regression 전체를 **연속 2번 통과**(가끔 실패하는 문제를 거르기 위해) |

**prepare (구현 전 점검)**

| 점검 | 내용 |
|---|---|
| 버그인가? (문서 규칙 검사) | 요청이 `PRD.md`·`INTENT.md`가 정한 동작과 현재 동작이 다른 것인지 본다. 정한 동작이 없거나 모호하면, 확정된 동작을 바꾸자는 요구 변경이거나 범위 밖(PRD 10장)이면 → HITL |
| 배경 이해 | 사용자가 어떤 상황인지 근거를 들어 말할 수 있나. 추측이 필요하면 이해하지 못한 것 → HITL |
| 목적 이해 | 왜 고쳐야 하고, 고치면 무엇이 달라져야 하나 |
| 규모·위험 | 변경이 너무 크거나 위험이 높은데 사용자가 모르면 경고하며 HITL |
| 재현·원인 (버그수정) | 재현 방법(단계·입력·기대와 실제)을 실제로 재현해 증거를 남기고, 원인 코드 위치를 찾고, 같은 증상이 다른 곳에 있는지 본다(있으면 기록만 하고 이번 범위에 넣지 않음). 재현하지 못하면 → HITL |
| 영향 범위·기존 테스트 | 바꿀 파일, 관련 JUnit·E2E, 테스트 공백 |
| 최소 수정 계획 | 원인 한 곳만 고치는 계획과 재발 방지 테스트(재현 테스트가 있으면 `test.fail()` 제거, 없으면 먼저 실패하는 테스트를 만든 뒤 고침, 새 테스트는 1~2개). Lint·Formatter·리팩토링은 하지 않음 |
| 체크리스트 3개 | 기본 틀: ① 재현 절차가 수정 후 기대 동작이 된다 ② 재발 방지 테스트가 있고 통과한다 ③ 기존 Regression Test 전체가 기대한 결과다 |

**implement (수정)**
- Plan을 세우고, 계획에 있는 것만 최소한으로 고치고, 빌드·테스트로 스스로 확인한 뒤 보고합니다.

**verify (구현 후 검증)**

| 검증 | 내용 |
|---|---|
| 체크리스트 3개 | prepare가 정한 항목을 하나씩 확인 (충족 / 미충족 / 확인 못 함) |
| Regression Test 전부 | JUnit(`./gradlew test`)과 E2E(`src/test/e2e` 전체)를 하나도 빼지 않고 실행 |
| 재현 절차 재실행 | 수정 후 코드로 재현 절차를 다시 실행해 문서가 정한 기대 동작이 나오는지 |
| 재발 방지 테스트 | 이번 버그를 직접 검증하는지(상태 코드만 보는 약한 검증이 아닌지), 이번 버그의 `test.fail()`이 제거되어 통과하는지. 다른 버그의 `test.fail()`은 그대로 실패해야 정상 |
| 최소 수정 확인 | 바뀐 파일·줄이 계획과 맞는지. 원인과 무관한 변경이 섞였으면 FAIL |

**사람이 확인하는 곳 (HITL)**
- **버그수정:** prepare가 이해하지 못했거나, 큰 변경·높은 위험을 사용자가 모를 때만 멈춥니다. 평소에는 사람이 중간에 끼지 않고 Loop가 끝까지 돕니다.
- **기능개발:** 구현 전에 사람이 점검 결과와 계획을 보고 **승인**합니다. 승인 전에는 코드를 바꾸지 않습니다. 구현 뒤에는 verify가 PASS면 끝나고, 결과는 사람이 `report.html`로 확인합니다.

## 5. 끝나는 조건

| 종료 | 조건 |
|---|---|
| `done` | 체크리스트 3개 충족 + Regression Test 모두 기대한 결과(기능개발은 연속 2번). Report를 만들고 종료 |
| `hitl` | prepare가 사람 확인을 요청. 질문·경고를 돌려주고 수정하지 않음 |
| `max_rounds` | 3회차까지 돌았는데도 검증이 통과하지 못함. 실패 내용과 피드백을 돌려줌 |
| `failed` | prepare·implement·verify 중 하나가 결과를 내지 못함 |

## 6. 산출물

```
docs/evidence/yeri/{작업번호+작업명}/     예: BUG-001-cancel-redirect, DEV-002-factory-operating-cost
├─ precheck.html   구현 전 점검 내용 (요청 요약, 배경·목적 이해, 규모·위험, 재현·원인, 영향 범위, 계획, 체크리스트 3개)
└─ report.html     구현 요약, 바뀐 파일, 빌드·테스트 결과, 반복 횟수, 남은 문제

docs/logs/
├─ prepare/inspection_날짜_시간_초.log   점검 기록 (HITL로 끝나도 남음)
├─ verify/review_날짜_시간_초.log        검증 기록 (PASS·FAIL 모두 남음)
└─ reports/report_날짜_시간_초.HTML      PASS일 때만 만드는 Report (세 단계가 한 일을 짧게 정리)
```

- **작업 폴더 이름:** `작업번호-작업명`. 작업번호는 유형별로 순서대로 붙입니다. 버그수정은 `BUG-001`, `BUG-002`, 기능개발은 `DEV-001`, `DEV-002`처럼 쓰고, 작업명은 내용을 알 수 있는 짧은 영어 소문자와 하이픈으로 씁니다. (예: `BUG-001-cancel-redirect`, `DEV-002-factory-operating-cost`) 작업마다 폴더가 따로라 이전 작업의 점검·보고가 덮어써지지 않습니다.
- precheck.html과 report.html은 공용 템플릿(`docs/templates/precheck.template.html`, `report.template.html`)을 복사해 채웁니다. 워크플로가 `{{` 남음, 배너 남음, 템플릿 버전, `data-loop`·`data-status` 값을 확인하고, 어기면 에이전트에게 한 번 고치게 합니다.
- `report.html`은 verify가 **PASS일 때만** 만듭니다. FAIL이면 폴더에는 `precheck.html`만 있고, 검증 로그만 남깁니다. (`docs/logs/reports/`의 Report와 같은 내용입니다.)
- 같은 버그를 prepare로 되돌아가 다시 돌면(Feedback Loop) 같은 작업 폴더의 `precheck.html`을 그 회차 점검 내용으로 갱신하고, 이전 실패와 원인을 함께 적습니다.

## 7. 지키는 규칙

- 개발 앱(8080)과 개발 DB(`./data/battery`)는 건드리지 않습니다. E2E는 별도 포트·별도 DB로 띄운 앱에 돌립니다.
- commit, push, PR은 자동으로 하지 않습니다. 사람이 요청할 때만 합니다.
- 확인하지 못한 것은 "확인하지 못함"이라고 적고, 통과했다고 쓰지 않습니다.
- 일부 테스트만 골라 돌리지 않습니다. 검증에 실패했다고 테스트나 `test.fail()`을 마음대로 바꾸지 않습니다.
- 범위 밖으로 확정된 것(PRD 10장)은 고치지 않습니다. (예: 중복 확정 방지)
- **기능개발 전용:** 코드 수정은 구현 전 계획 승인 뒤에만 합니다. 계획에 없는 파일은 멈추고 보고합니다. 사용자가 답해서 정해진 빈칸은 문서(PRD·INTENT)에 반영하고, 요구 변경은 아니라고 로그에 남깁니다.
- **기능개발 전용:** 원인을 코드로 확인하지 못했다면 코드를 고치지 않습니다. 그 사실을 적고 다시 돌리되, 수정 없이 통과해도 "가끔 실패하는 문제 의심"으로 남깁니다.

## 8. 구현 위치와 현재 상태

| 구성 | 위치 | 상태 |
|---|---|---|
| 워크플로 | `.claude/workflows/ih.js` | 있음. 작업번호-작업명 폴더를 정하고, 공용 템플릿 규칙과 필수 산출물(점검·검증 로그, Report)을 확인해 빠지면 대신 만들거나 한 번 다시 요청함. 에이전트 없이 흐름만 시험(통과, 실패 후 재시도, HITL, 횟수 초과, 로그 누락, 템플릿 위반)했음 |
| Subagent | `.claude/agents/prepare.md`, `implement.md`, `verify.md` | 있음. prepare·verify는 버그수정용 지침과 공용 템플릿·작업 폴더 규칙 반영. implement는 공통 지침 |
| 공용 템플릿 | `docs/templates/precheck.template.html`, `report.template.html` | 있음 (PR #15) |

**아직 하지 않은 것**
- 실제 에이전트로 한 번 돌려 보는 것. 에이전트 정의와 워크플로를 고친 뒤에는 `/reload-skills`를 해야 `/ih`가 최신 정의로 돕니다. (한 번 옛 정의로 돌아 로그와 템플릿이 반영되지 않은 적이 있음)

## 9. 테스트 계획

확인용 버그로 Loop를 한 번 돌려 봅니다.

> 주문을 취소한 직후 삭제된 주문의 상세로 이동해 HTTP 500 오류 화면이 뜬다. 취소 직후 **주문 목록으로 이동**하게 고친다. (INTENT 9장 1번, E2E-033)
